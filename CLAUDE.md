# CLAUDE.md

## Project Overview

Streamlit application for structured extraction, document understanding, and template generation with NuMind NuExtract on Apple Silicon with MLX. Uses `numind/NuExtract3-mlx-8bits` (a 4B-parameter Qwen3-family vision-language model) via [mlx-vlm](https://github.com/Blaizzy/mlx-vlm). Mirrors the official [NuExtract3 HF Space](https://huggingface.co/spaces/numind/NuExtract3) architecture but uses local MLX inference instead of remote vLLM.

Three modes: structured JSON extraction (typed template + image/text → JSON), document-to-markdown (image → Markdown), and template generation (NL description → JSON template). Streaming output with optional `<think>...</think>` reasoning trace.

## Commands

```bash
uv sync                                       # Setup environment
git config core.hooksPath .githooks           # One-time per clone: enable the pre-push gates
uv run streamlit run streamlit_app.py         # Run the app
uv run --frozen ruff check .                  # Lint (CI gate)
uv run --frozen ruff format --check .         # Format check (CI gate); drop --check to rewrite
uv run --frozen ty check                      # Type check (CI gate)
uv run --frozen pytest                        # Tests (CI gate)
uv run --frozen pytest tests/test_nuextract.py::test_name   # Run a single test
uv lock && uv sync                            # After editing [project.dependencies]
uv run python scripts/probe_mlx_vlm.py        # Model probe — ~5 GB download, details below
```

**Always `--frozen` for the gates.** A bare `uv run` locks and syncs by default, silently rewriting an out-of-date `uv.lock` in the working tree; see the pre-push section for why that reddens `main`.

When working with Python, invoke the relevant `/astral:<skill>` for uv, ty, and ruff. For anything touching Streamlit, invoke `developing-with-streamlit` — it loads docs matched to the installed version, which matters here (see the Streamlit pin in Key Details).

CI via GitHub Actions (`.github/workflows/ci.yml`): lint, format check, type check, and `pytest` gate **every branch push** (`branches: ["**"]`), pull requests, and `workflow_dispatch`; a `release` job runs after them (below). Runs on `macos-15` (Apple Silicon) for MLX compatibility — **not `macos-14`**, which GitHub retires on 2026-11-02 ([actions/runner-images#13518](https://github.com/actions/runner-images/issues/13518)); `macos-26`/`macos-latest` is the next step up, but that image has an open Metal-toolchain gap worth checking first, since MLX is Metal. The unfiltered `pull_request` trigger exists for **fork** PRs — a push inside a fork does not trigger this repo's workflows — and is safe precisely because it is `pull_request` (read-only token, no secrets) and never `pull_request_target`. Its one cost: a *same-repo* branch with an open PR runs twice, once per event.

**Token scope is two-tier.** Workflow-level `permissions: contents: read` keeps the `test` job — which runs fork-PR code — from inheriting a widened repo default; `contents: write` is re-granted only on the `release` job. Drop the job-level grant and `gh release create` fails; drop the workflow-level one and the token silently widens for fork PRs.

**`timeout-minutes: 15` is load-bearing, not hygiene.** Without it a hung step burns GitHub's 360-minute default — which has already happened twice, both runs cancelled at exactly 6h inside `Run tests` (IDs in `ci.yml`). A timeout lands as `cancelled`, not `failure`, so **no failure notification fires** and the next green push quietly paints over it. The repo is public, so the runners are free: nothing bills you into noticing.

**There is no *workflow-level* `concurrency` block; the `release` job carries its own.** The removed workflow-level one keyed `main` on `github.run_id` — unique per run, so the group always held exactly one member by construction and could never dedupe anything. Since `15b8480` enabled branch CI, restoring it is a live trade-off: superseding stale branch runs would save wall-clock, against which these runners are free here and redundant runs cost only noise. If you do restore it, copy the expression exactly:

```yaml
group: ${{ github.workflow }}-${{ github.ref == 'refs/heads/main' && github.run_id || github.ref }}
cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}
```

The `run_id` ternary is not optional — GitHub unconditionally cancels an already-*pending* run in a group when a new one queues, so a group keyed on plain `github.ref` would kill queued `main` runs, and it would do so silently (a cancel raises no failure notification, per the paragraph above). Note also that `concurrency` can never dedupe a `push` run against a `pull_request` run for the same commit: those land in different groups.

**Nearly everything CI depends on is pinned**, so a green build rarely turns red without a repo change: Python deps via `==` + `uv sync --locked`, the interpreter via `.python-version` (3.13), uv itself via setup-uv's `version:` input, and setup-uv by exact tag. **`--locked`, not `--frozen`** — `--frozen` installs whatever `uv.lock` says and never checks it against `pyproject.toml`, so a dependency edit that was never relocked passes CI green while testing the *old* pins; `--locked` asserts the two agree and fails if they don't. Three inputs still float: `actions/checkout@v7` is a moving major tag (setup-uv cannot do the same — it stopped publishing moving majors after `v7`, hence the exact `@v10.2.0`; bump it in the same commit as the `version:` input, since each setup-uv release ships known checksums only for the uv releases up to its own date), the `release` job's `ubuntu-latest` is a moving image alias (it needs no Apple Silicon — it only calls the GitHub API), and `macos-15` is on a deprecation clock.

**Releases are automated inside `ci.yml`; there is no `release.yml`** (it was deleted). A `release` job with `needs: test` runs only on a `push` to `main`, reads `[project].version` from `pyproject.toml`, and if no `v<version>` tag exists yet creates the tag *and* the GitHub Release in a single `gh release create --target <sha>` call. The whole procedure is therefore **bump the version, commit, push** — no `git tag` step, because the tag is derived *from* the version rather than checked against it. Four non-obvious constraints shape this:

- **A tag-triggered workflow cannot be part of the chain.** Per GitHub, *"events triggered by the `GITHUB_TOKEN` will not create a new workflow run"* — so a tag pushed by CI fires nothing and `on: push: tags:` is dead on arrival. The suppression covers **event delivery only**; the Releases *API* works fine with `GITHUB_TOKEN`, which is why one `gh release create` both tags and releases and nothing ever `git push`es a tag. `needs: test` is consequently the only thing that actually guarantees the four gates ran on the released commit.
- **Bump detection asks "does tag `v<version>` already exist?", never a `github.event.before..github.sha` diff.** A state question is idempotent: re-running the workflow, force-pushing, or pushing ten commits at once each still produce exactly one release. A diff question breaks in all three.
- **Notes come from the commit log, not `--generate-notes`.** GitHub builds auto-notes by summarising merged pull requests; this repo releases straight from `main` and has never had one, so `--generate-notes` would emit little more than a compare link. The job writes `git log <prev-tag>..HEAD` to a file and passes `--notes-file`, which also keeps commit subjects out of the shell. The baseline is `git describe --match 'v[0-9]*'`, not a bare `git describe` — an unrelated tag would otherwise become the baseline and silently truncate the range. The prerelease test is `case "$VERSION" in *[!0-9.]*)` — any version containing a character other than digits and dots (`1.3.0rc1`, `1.3.0.dev1`) ships `--prerelease` so it cannot take the Latest badge; a digits-and-dots version always ships as a full release.
- **The job needs its own `concurrency` group** (`release-${{ github.ref }}`, `cancel-in-progress: false`). It is check-then-act — *does `v<version>` exist?* then *create it* — so two pushes landing inside that window would both decide to release, and the loser dies on "release already exists", reddening `main`.

The `v1.2.0` release was created by hand and predates all of this — and since `pyproject.toml` is still at `1.2.0`, the release job has only ever taken its skip path. **The `gh release create` step has never executed in CI**; watch the first version bump closely.

**Workflow: local `type/kebab-summary` branch → `--no-ff` merge into `main` → push. There are no PRs.** Commit subjects are Conventional Commits (`ci:`/`feat:`/`fix:`/`chore:`/`docs:`/`test:`/`refactor:` + lowercase summary) — not a style preference: the release job pastes non-merge subjects verbatim into the public GitHub Release body, so a sloppy subject ships. Keep the merge commit (`--no-ff`); `--no-merges` excludes it from the notes, so it records the branch without adding noise.

Lint/type config lives in `pyproject.toml`: Ruff selects `E`/`F`/`I` (import sort)/`UP` (pyupgrade), with line length deferred to the formatter (`ignore = ["E501"]`); ty targets the `requires-python` floor (3.12) with `error-on-warning`. **The runtime/type-check version split is deliberate** — code runs on 3.13 (`.python-version`) while ty analyzes against the 3.12 floor, so `requires-python = ">=3.12"` stays honest without holding the runtime back.

Conventions ruff does **not** enforce, so new code has to carry them by hand: app and script modules open with a module docstring then `from __future__ import annotations` (test modules do neither); every function has a docstring; functions go keyword-only after the leading positionals (`def f(a, *, b, c)`); module-private helpers are `_`-prefixed; and any non-obvious decision carries a comment saying *why*, not what.

Team-shared Claude Code config in `.claude/` (tracked in git) enforces these same gates at edit-time, via **one** hook plus declarative permissions. Note that `.gitignore` excludes the *contents* of `.claude/` and `docs/` and re-includes by exception (`!.claude/settings.json`, `!.claude/hooks/`, `!docs/*.png`) — git cannot re-include a file whose parent directory is excluded, so anything new you add there (a `.claude/agents/…`, a non-PNG doc) is silently untracked until you add a matching `!` negation.

- **`.claude/hooks/py-checks.sh`** (PostToolUse) — after each `.py` edit: `ruff check --fix` → `ruff format` → **`ruff check`** → `ty check`. **Lint-fix before format is Astral's recommended order** — fixes rewrite code structure (`I` re-sorts imports, `UP` rewrites syntax), so formatting last guarantees formatted output whatever the fixer did. **Lint is checked twice on purpose** — the reported verdict must come from a pass over the *final* bytes, since the first two steps mutate the file; reporting step 1's output would give line numbers pointing into the pre-format file and could exit 0 on a lint-dirty result. These four calls are bare `uv run`, not `--frozen`, so a `.py` edit made while `uv.lock` is stale **relocks it in the working tree** — which then lets pre-push's `uv lock --check` pass over a stale *committed* lock. Commit `uv.lock` alongside any `pyproject.toml` change. Needs `jq` + `uv`; missing `jq` degrades to a silent no-op.
- **`permissions.deny` in `.claude/settings.json`** — denies `Read` *and* `Edit` on `.env*` and `.streamlit/secrets.toml`. Replaced a `PreToolUse` hook; broader on **tool coverage**, since permission rules sit above tool dispatch and so also block **reads**, which a matcher scoped to `Write|Edit|MultiEdit` never did. Four things in that list look like redundancy and are not — **read `.claude/hooks/README.md` before "simplifying" any of them**:
  - Each path is listed **twice**, `/…` and `**/…`: `/.env*` anchors at the project root, `**/.env*` matches at any depth under the cwd. (The `./.env` form in Claude Code's own docs anchors to `<cwd>` alone and misses the project's `.env` from a subdirectory.)
  - **`.env*`, not `.env` + `.env.*`** — one glob also covers `.envrc`, a common `HF_TOKEN` home. `.gitignore` uses `.env*` for the same reason, so the two lists stay in sync.
  - The **`.[eE][nN][vV]*` duplicates** restore case-insensitive coverage of `.ENV` on macOS; the plain rules stay alongside so the class rules can only add coverage, never silently replace it.
  - **No `Write(...)` rule, deliberately** — file permissions are checked against `Edit(path)`/`Read(path)` only; a `Write`/`MultiEdit`/`NotebookEdit` rule is accepted, never consulted, and warns at startup. `Edit` covers every built-in editing tool, and `Read` is listed alongside it because a `Read` deny does not cover `NotebookEdit`.

  **Accident guardrail, not a security boundary — and the bypass is live here.** Deny rules do not reach arbitrary subprocesses, and `.claude/settings.local.json` allowlists `Bash(uv run *)`, so `uv run python -c "print(open('.env').read())"` prints `HF_TOKEN` into context with no rule firing. They stop the accident, not a determined path.

**Tests are not a Claude Code hook — they are a git hook.** A `Stop` hook that ran `pytest` was removed: it cost ~9s per turn and keyed on working-tree state, so any dirty `.py` file made it fire on every turn, including pure-conversation ones. Its job moved to `.githooks/pre-push` — the right granularity (once per *push*, not per turn), and it protects a hand-typed `git push`, which no agent hook can. It runs **`uv lock --check` plus all four CI gates**, cheapest first (`uv lock --check` → `ruff check` → `ruff format --check` → `ty check` → `pytest`), aborting at the first failure: gating on `pytest` alone would let a lint or type error push cleanly onto `main` and turn CI red there. It deliberately uses no `--fix` and no bare `ruff format` — a hook that rewrites the tree mid-push would make the tested tree differ from the reviewed one.

**`uv lock --check` runs first, and every gate runs under `uv run --frozen`, for one reason:** `uv run` locks and syncs by default, so a bare `uv run` silently *rewrites* an out-of-date `uv.lock` in the working tree. Every gate would then pass against the regenerated lock while the committed lock stayed stale, the push would succeed, and CI's `uv sync --locked` would fail on `main` — the precise failure this hook exists to stop. It is **opt-in per clone**, since git does not share hooks: `git config core.hooksPath .githooks`. The hook skips deletion-only pushes, warns when the tree has uncommitted *or untracked* changes (it tests the tree, not the pushed commits — and `git diff` alone is blind to untracked files that pytest still collects), and is bypassed with `git push --no-verify`.

Hooks are snapshotted at session start, so restart after pulling changes. Details in `.claude/hooks/README.md`; personal overrides go in the gitignored `.claude/settings.local.json`.

## Architecture

App in `streamlit_app.py`, runtime wrapper in `nuextract.py`, probe in `scripts/probe_mlx_vlm.py`.

### `nuextract.py`

Thin wrapper around mlx-vlm. Module-level imports of `huggingface_hub.snapshot_download`, `mlx_vlm.load as mlx_vlm_load`, `mlx_vlm.stream_generate as mlx_vlm_stream_generate` — so tests patch `nuextract.snapshot_download` / `nuextract.mlx_vlm_load` / `nuextract.mlx_vlm_stream_generate` (standard "patch where used" pattern). The aliases are the patch targets; `nuextract.load`/`nuextract.stream_generate` do not exist.

- **Constants** — `DEFAULT_MODEL_ID = "numind/NuExtract3-mlx-8bits"`, `DEFAULT_MODEL_REVISION` (a full commit SHA — see *Pinned model revision* in Key Details), `DEFAULT_MAX_TOKENS = 4096`, `DEFAULT_TEMPERATURE = 0.0`, `MODE_STRUCTURED = "structured"`, `MODE_CONTENT = "content"`, `MODE_MARKDOWN = "markdown"`, `MODE_TEMPLATE_GENERATION = "template-generation"`.
  **`MODE_STRUCTURED`/`MODE_CONTENT` are value-asserted by tests but intentionally never passed by the app.** Structured extraction sends `template=...` with `mode=None` (the Jinja infers `structured` from the template), and `_run_mode` detects exactly that: `is_structured = template is not None and mode is None`. Passing `MODE_STRUCTURED` explicitly to "tidy up" the extract handler flips `is_structured` to False and downgrades the Result pane from a JSON code block to plain markdown. The AppTest streaming tests catch it (they assert the code block), but nothing flags the two constants as load-bearing. Deleting the two "unused" constants breaks `test_nuextract.py`.
- **`load_model(model_id, *, revision=DEFAULT_MODEL_REVISION)`** — `snapshot_download(repo_id=..., revision=...)` → `mlx_vlm.load`, with the snapshot's `processor_config.json` loaded exactly as downloaded (see Key Details for why it is not patched). Returns `(model, processor)`. The revision default belongs to `DEFAULT_MODEL_ID`, so a caller overriding `model_id` must pass its own (`None` tracks `main`).
- **`build_messages(text, image_path, system_prompt)`** — Builds a chat message list: optional `{"role": "system", "content": ...}` first (string-only — the Jinja raises if it contains images), then a `{"role": "user", "content": [...]}` with `{"type": "image", "image": path}` and/or `{"type": "text", "text": ...}` parts. The Jinja template inserts the vision placeholder; actual pixel data flows separately via `stream_generate(image=...)`.
- **`render_prompt(processor, messages, *, template, instructions, mode, enable_thinking)`** — Calls `processor.apply_chat_template(...)` with task kwargs **inline** (HF transformers convention), NOT nested under `chat_template_kwargs` (that's a vLLM-specific convention). Omits `None`/empty values so the template's defaults apply.
- **`stream_extract(model, processor, *, text, image_path, system_prompt, template, instructions, mode, enable_thinking, temperature, max_tokens)`** — Builds messages → renders prompt → calls `mlx_vlm.stream_generate`. Yields **cumulative** text on each chunk (not per-chunk deltas) for direct rendering into a Streamlit placeholder.
- **`split_reasoning_and_output(text, reasoning_enabled)`** — Splits on `</think>` (case-insensitive). Returns `("", text)` when reasoning is off; returns `(text, "")` when reasoning is on but `</think>` hasn't arrived yet.
- **`extract_answer_block(text)`** — Pulls `<answer>...</answer>` contents if present, else the longest span at any `{` position that parses via `json.JSONDecoder.raw_decode`, else the stripped text. Correctly handles the "reasoning text + JSON" case without merging unrelated spans.
- **`pretty_json_or_text(text)`** — Tries `json.loads` + indented re-dump; falls back to the original on parse failure.

### `streamlit_app.py`

Sidebar plus a two-column main area. Sidebar: generation settings only. Left: inputs, split across a **Document** and a **Template** tab. Right: action buttons + outputs (wrapped in an `st.fragment`).

- **`get_model()`** — `@st.cache_resource` wrapper around `nuextract.load_model`. **It returns the exception rather than raising it, so a *failed* load is cached too.** `st.cache_resource` writes an entry only when the function returns (`cache_utils.py`'s `_handle_cache_miss` reaches `write_result`, through its `_store_computed_value` helper, only on the success path), so a raising load is a fresh cache miss on every rerun. That was harmless while the load blocked the whole page — nothing had rendered, so nothing could trigger a rerun — but the input widgets now paint first and stay live through a failure, which would turn every slider drag into another download attempt. The call site branches on `isinstance(loaded, Exception)` and offers an explicit **Retry model load** button that calls `get_model.clear()`; making retry a deliberate click is the entire point, so do not "simplify" this back to a bare `return load_model()`. The failure renders in three parts, and the split is deliberate: a one-line `st.error` headline naming the exception type, the message through `st.code` because `st.error`'s body is GitHub-flavored Markdown with soft breaks disabled and this path's real failures (an offline hub download, or the eight-line `requires the PyTorch library` error a swallowed mlx-vlm processor failure surfaces as — see *No torch* in Key Details) are multi-line, and the traceback inside a collapsed `st.expander` — since `get_model` returns the exception instead of raising it, Streamlit never reports it and nothing logs it, so `st.exception(loaded)` is the only place the frame that names the cause survives. That whole branch still has no test; `key="retry_model_load_button"` exists to make covering it possible.
- **`_save_uploaded_image(uploaded_file)`** — Persists `st.file_uploader` bytes to a temp file once per upload, keyed on `uploaded_file.file_id` in `st.session_state`. Reruns return the cached path; a new upload deletes the previous temp file before writing the new one, and removing the upload deletes the orphaned temp file and clears the cached `session_state` keys. Required because mlx-vlm wants file paths/URLs.
- **`_validate_template(template_str)`** — Validates JSON template is a non-empty dict; returns `(parsed, error)`.
- **`_render_output_pane(output_placeholder, reasoning_placeholder, accumulated, *, reasoning_enabled, is_structured, final=False)`** — Updates both panes from a single stream chunk: routes reasoning trace to its placeholder (or shows `_(reasoning disabled)_` when the run being painted had reasoning off — template generation, or a replay from before the toggle was switched on), then renders output as JSON code-block (structured/template-gen modes) or markdown (markdown mode). Shows `_(waiting for output after </think>)_` placeholder while reasoning is in progress. `reasoning_placeholder` is `None` while the Reasoning pane is hidden (see `_output_section`); the trace is then still **split off**, just not drawn, so a replayed reasoning run never leaks its trace into the Result pane. That leak is visible only in markdown mode — in structured mode the final pass's `extract_answer_block` digs the JSON out of the trace on its own — which is why `test_render_output_pane_hidden_reasoning_pane_still_splits_the_trace` and `test_switching_reasoning_off_hides_a_stored_trace_without_leaking_it` both use markdown mode (an extract-mode version of the latter passed with the split removed). Two details are load-bearing:
  - **`final` gates `extract_answer_block` + `pretty_json_or_text` to the one post-stream call.** Those helpers have a *whole-document* contract — `extract_answer_block` returns the longest span that **parses** — which every intermediate chunk violates: mid-stream the outer object is still truncated, so the longest parsing span is whichever *nested* object closed first. Running them per chunk (as the code did until `final` existed) makes the Result pane grow normally, then visibly **shrink** to a nested sub-object and sit frozen there until the last token, when it snaps to the full document. Reproduce with `extract_answer_block(full_json[:85%])`. `_run_mode` therefore streams the raw partial and calls back once with `final=True`, placed **after** the empty-output guard — above it, an empty run repaints `_(generating...)_` over its own warning — and **gated on `render_as_json`**, since for markdown mode the final render is byte-identical to the last streaming one and would re-send the largest document the app produces. Regression tests: `test_render_output_pane_streaming_partial_json_is_not_collapsed`, `..._final_extracts_answer_and_pretty_prints`, and `test_completed_run_strips_answer_wrapper_and_pretty_prints` — the last one is the only cover for the **call site**, and it asserts the exact indented body (`'{\n  "k": 1\n}'`) precisely because a substring assertion passes whether or not the final pass ran at all.
  - **The streaming branch renders unconditionally as `st.code(..., language="json", wrap_lines=True)` and never inspects the partial.** An earlier revision prefix-tested `("{", "[", "<answer>")` to pick code-vs-markdown; that is the wrong shape and was reverted. Any preamble (`Here is the extraction:\n{...}`), an `<ANSWER>` wrapper in the wrong case (`_ANSWER_RE` is `IGNORECASE`, a literal prefix test is not), or a stray `<think>` when reasoning is off routes the whole run's JSON through the Markdown renderer — the same untrusted-output-into-Markdown class as the reasoning-pane fence below. Structured mode is *asking* for JSON, so it renders as JSON and only the final pass — whose input `extract_answer_block` has already cleaned — decides prose-vs-JSON. `wrap_lines=True` matters more here than it looks: the streamed partial is the model's raw output, so compact JSON would otherwise be one long horizontally-scrolling line whose visible portion stops changing.
  - **The reasoning trace goes through `st.code(think, language=None, wrap_lines=True)` inside `reasoning_placeholder.container(height=300, autoscroll=True)`, never a hand-built ` ```text ` fence.** **Both the fixed height and the autoscroll are load-bearing, and the height must sit on the container rather than on `st.code`.** The pane has to scroll rather than grow, because the Result pane and its download button sit *below* it. But `st.code` exposes no autoscroll, and `_render_output_pane` re-creates this element on every chunk, so a bare `st.code(height=300)` pins the viewport to the *top* of the trace: the newest tokens stream in below the fold and any manual scroll is undone by the next chunk — strictly worse than growing, where the newest text was at least always visible. Regression test: `test_reasoning_trace_is_height_capped_and_tail_follows`, which asserts the container call because no output assertion can see either property. `think` is untrusted model output; a fence *inside* it closes the wrapper and hands the remainder to the Markdown renderer (headings render, tables render, ` ```mermaid ` renders as a diagram). Markdown-mode reasoning quotes fences routinely, so this fires in normal use. `language=None` — not `"text"` — is the documented spelling for plain monospace. Regression test: `test_reasoning_trace_containing_a_code_fence_stays_in_one_element`.
- **`_download_payload(accumulated, *, download_kind, reasoning)`** — Splits off the reasoning trace, then applies `extract_answer_block` when `_DOWNLOAD_CONFIGS[download_kind]`'s 4th field says the mode is JSON. Returns the exact text a download would write. **It is also the only honest emptiness test, and `_run_mode`'s completion guard uses it for exactly that reason.** Guarding on `accumulated` — as the code did originally — passes two runs that produced no answer whatsoever, because the raw text still carries the trace and the wrapper: (1) reasoning on with the token budget spent before `</think>` ever arrives, which ended the run showing the *mid-stream* `_(waiting for output after </think>)_` caption as its terminal state, and (2) a closed but empty `<answer></answer>`, which blanked the Result pane at the final render. Both then rendered a download button whose payload was `""`. Regression tests: `test_reasoning_that_never_closes_warns_instead_of_stalling`, `test_empty_answer_wrapper_warns_instead_of_blanking_the_pane`. Case (1) gets its own warning naming Max tokens and the Reasoning toggle, since unlike a genuinely empty response it has a remedy the user can reach.
- **`_render_download_button(placeholder, payload, *, download_kind)`** — Renders a `st.download_button` for an **already-cleaned** payload, with `on_click="ignore"` so downloading stays client-side and doesn't rerun the fragment (a rerun would repaint the idle hint over the result and drop the button). `download_kind` selects label, filename and mime. It deliberately does **not** clean the text itself any more: `_run_mode` needs the payload before this call in order to guard on it, and deriving it twice is how the guard and the button drift apart.
- **`_render_completed_run(state, *, output_placeholder, reasoning_placeholder, download_placeholder, streamed_live=False)`** — The **single** terminal-render implementation, shared by `_run_mode` and `_output_section`'s replay so the two cannot drift about what a finished run looks like. `streamed_live` is the one place the mode asymmetry lives: straight off the stream the panes already hold the last streaming paint, and in markdown mode the final pass reproduces it byte for byte, so it is skipped — re-sending the largest document the app produces for no visible change. A replay never qualifies, because its placeholders were just re-created empty and there is nothing for the paint to match.
- **`_stored_run()`** — Reads `_LAST_RUN_KEY` and returns `None` unless the value is a dict carrying every field in `_LAST_RUN_FIELDS`. **Shape-checked rather than subscripted, because Streamlit hot-reloads an edited script into the *same* session with `session_state` preserved**, so a stored dict outlives the code that wrote it and a renamed field would raise `KeyError` in a live session — the app's own dev loop.
- **`_run_mode(...)`** — Drives one streamed generation: calls `_render_output_pane` on every chunk yielded by `stream_extract`, then re-renders once with `final=True` and fills the download placeholder on completion. `render_as_json = is_structured or mode == MODE_TEMPLATE_GENERATION` is computed once and passed to both calls; letting the two drift is how the final render silently disagrees with the streaming one. On the success path it builds one `state` dict (`accumulated`, `payload`, `download_kind`, `reasoning`, `render_as_json`), stores it under `_LAST_RUN_KEY`, and hands it to `_render_completed_run(..., streamed_live=True)` — so the run it just finished and any later replay are painted by the same code. Built **below** the empty-payload guard, so a run that produced no answer can never become a replayable result, and it carries `payload` rather than re-deriving it for the same reason `_render_download_button` does not clean its own text.
- **`_output_section()`** — `@st.fragment`-decorated, **takes no arguments**. Renders the three action buttons — the primary **Extract JSON** on its own full-width row, **Convert to Markdown** and **Generate template** sharing a horizontal container beneath it — then the Reasoning pane **only while the `reasoning_checkbox` toggle is on**, then the always-rendered Result placeholder and the download placeholder. The two button rows are deliberate: all three on one row need ~493px (measured natural widths plus gaps — a `width="stretch"` button in a horizontal container is `flex: 1 1 fit-content`, so it wraps only when natural widths overflow), and with the sidebar open this column reaches that only from a ~1480px viewport up. Below it — the 13-inch MacBook Air's 1440 and 1470px included — a single horizontal container wrapped and left **Generate template** stretched full-width on a row of its own. Two rows look the same at every width; the secondary pair alone needs ~351px. The Reasoning pane is keyed to the *toggle*, not to the run: when a button fires the toggle is the run's setting, and on a replay the pane follows the current choice, so switching reasoning off hides a stored trace and switching it back on replays it (regression tests `test_reasoning_pane_appears_only_while_the_toggle_is_on` — asserted after a completed toggle-off run, since the idle page never painted the caption, and then across the replay when the toggle goes on — `test_switching_reasoning_off_hides_a_stored_trace_without_leaking_it`, and `test_template_gen_forces_reasoning_off`, which checks the pane says `_(reasoning disabled)_` rather than keeping `_(no run yet)_`). The Result pane shows an idle empty-state hint until a run produces output, and when shown the Reasoning pane is captioned `_(no run yet)_` **at placeholder creation** rather than only on the idle path — every path that ends without a trace leaves it unwritten, including a validation warning, and a bold header over an unwritten `st.empty()` renders as a void; regression test `test_validation_failure_leaves_the_reasoning_pane_captioned`, which switches the toggle on first). It **then calls `get_model()` itself**, then runs the button handlers. Loading inside the fragment rather than accepting a loaded pair is what lets the ~5 GB download sit below this section's own chrome: nothing on the page waits on it except the Result slot the output lands in, which shows the spinner. Reverting to `_output_section(model, processor)` necessarily moves the load back above the buttons and is caught by `test_model_loads_after_the_page_chrome_renders`. Lives in a fragment so clicking a generate button reruns **only** this region — the sidebar and left-column input widgets keep their state and aren't re-rendered during generation. The buttons must be inside the fragment for that isolation to apply (by default a fragment only reruns independently when the triggering widget is inside it; since Streamlit 1.63 an outside widget can also target a *keyed* fragment via `st.rerun("<key>")` from a callback, which buys nothing here but more machinery). Reads input values from `st.session_state` by widget key (the sidebar and left-column widgets populate them on the full rerun that precedes the fragment). Handlers validate inputs (markdown requires image; extract requires template + either image or text) and call `_run_mode`. **When no button fired it replays `_stored_run()` through `_render_completed_run` instead of painting the idle hint**, because the sidebar and left-column widgets sit outside the fragment: touching any of them is a *full* rerun that re-creates the placeholders empty with no button pressed, which used to discard a finished result and its download button. **When a button *did* fire it first `pop`s `_LAST_RUN_KEY`, and that single line is the whole guard against replaying a superseded result.** Storing only on success is not enough: every failure path — a stream exception, an empty payload, or a validation error that never reaches `_run_mode` — leaves the *previous* run stored, so the next full rerun replays it with a live download button over the error the user just got, across modes as well (a failed markdown run resurrecting an extract result under "Download JSON"). Regression tests: `test_completed_run_survives_an_input_edit` and `test_failed_run_does_not_replay_the_previous_result`, both verified failing with their fix neutralized.
- **Top-level UI** — `st.set_page_config(page_icon=":material/document_scanner:", layout="wide")`, title (same icon), the `st.sidebar` block, then `st.columns([1, 1])` for the two panes. **The model-load spinner sits inside `col_right`, below the sidebar and the whole left column, and the ordering is load-bearing.** Streamlit emits a UI delta per `st.*` call, so a blocking call placed above the columns (where it used to be) stops *every* input widget from painting until the ~5 GB download finishes — the app renders a title and a spinner and nothing else. Loading after the sidebar and the left column means only the pane that actually needs the model waits. Keep `st.spinner` rather than `st.skeleton` here: the "~5 GB" text is what stops a multi-minute wait from reading as a hang. This is the ordering rule in `references/performance.md` ("Render stable UI before slow work") — which ships **inside the installed `streamlit` package** (`.venv/…/streamlit/.agents/skills/developing-with-streamlit/references/`) and **not in this repo**, so grepping for it locally finds nothing; reach it via the `developing-with-streamlit` skill.

  `test_model_loads_after_the_page_chrome_renders` gates the ordering. Render order is not observable from `AppTest`, so it asserts *structurally*: keyed widgets register themselves in `session_state` as they render, so an anchor key is present when `load_model` is called iff that widget already ran. **It checks three anchors, each the last keyed widget of its group, and "last" is load-bearing in every case** — an anchor further up still passes with the load sitting inside the group it is meant to guard. `reasoning_checkbox` is the last of the sidebar's 3 settings; `instructions_input` is the last of `col_left`'s 4 inputs (`template_input`, the 3rd, would permit a *mid-column* load); `template_button` is the last of the three action buttons (guarding the fragment's own chrome). The sidebar and the left column each get their own anchor because neither implies the other: either block can be moved below the load independently. Verified failing in all four directions: a load above `st.sidebar`, a mid-sidebar load, a mid-column load, and a load above the buttons. It also asserts `not at.exception` first, since a crash before any anchor would otherwise fail an ordering assertion and blame the wrong file. The `cold_model_cache` fixture clears `st.cache_resource` on both sides — `get_model` is cached process-wide, so without the pre-clear an earlier test's entry means the stub never runs and the assertion silently observes nothing, and without the post-clear the suite's cache keeps a pair built by a stub `monkeypatch` has already removed. Sidebar: a `Settings` subheader, temperature + max-tokens sliders and the reasoning toggle (keyed `reasoning_checkbox` still — an anchor above — though it is an `st.toggle`), and nothing else — a model-name caption was removed by request, and the layout test asserts the sidebar has no caption. Left pane: `st.tabs` with a **Document** tab (image uploader, preview, optional text area) and a **Template** tab (caption, JSON template editor, optional instructions). **Both tabs' widgets must run on every full rerun**, which is what the default `on_change="ignore"` gives: the fragment reads them from `session_state` by key and Streamlit drops the state of a widget that skips a run, so gating a tab's body on `.open` (lazy tabs) would make Extract see an empty template whenever the Document tab was showing. The selected tab survives full reruns (checked in a browser, since AppTest cannot observe tab selection). Image uploader (`max_upload_size=_MAX_IMAGE_UPLOAD_MB` = 25 — **a browser-side widget hint only**: `starlette_routes.py` enforces `server.maxUploadSize` and never reads the per-widget value, and no byte cap bounds *decode* memory anyway, since a 1 MB flat-colour 10000x10000 PNG still expands to ~300 MB of pixels; preview in `st.container(height=360, border=False)` — a **fixed** height, not a cap, since there is no max-height container and `st.image` has no height parameter, so tall scans scroll and anything shorter than 360px is padded; 360 is the tallest box that still keeps the whole Text box on screen beneath it in an 839px-tall viewport (400 cut it off by 30px), and `border=False` is explicit because a fixed-height container draws one by default). Every input is keyed, return values unused (read via `session_state` in the fragment). Right pane: `_output_section()` directly, with no subheader — its button rows line up with the tab bar. `test_settings_sit_in_the_sidebar_and_inputs_in_two_tabs` pins which region and tab holds each keyed widget.

**Adding a mode or a control.** A new mode touches five places: a `MODE_*` constant in `nuextract.py`; a `_DOWNLOAD_CONFIGS` entry (label, filename, mime, whether `extract_answer_block` strips wrappers); a keyed `st.button` inside `_output_section` (a secondary mode goes in the horizontal container beside **Convert to Markdown** — three secondaries need ~520px, so they would wrap below a ~1530px viewport with the sidebar open); an `elif` handler that validates inputs and calls `_run_mode`; and tests in all three files — then update the counts here *and* in README. A new input control must be a **keyed** widget outside the fragment — a setting in the sidebar, a document or task input in the matching left-column tab — whose return value is discarded and re-read as `st.session_state.get("<key>", <default>)` inside the fragment: a value captured at the widget call site is stale during a fragment-only rerun, because neither region re-executes. Add it to `test_settings_sit_in_the_sidebar_and_inputs_in_two_tabs`, and if it becomes the last widget of its region, move that region's anchor in the ordering guard. That is the whole reason for the keyed-widget pattern.

Changing the pane layout or any visible control invalidates `docs/screenshot-dark.png`, the single image README embeds (the light-theme companion was removed). **Bumping the `streamlit` pin invalidates it too** — `.streamlit/config.toml` sets only dark-mode colours, so everything else (radii, borders, fonts, and the whole Light theme) comes from the pinned version's built-in themes rather than from anything in this repo, and a dependency upgrade can repaint the app with no diff to point at. Editing the dark palette invalidates it as well. Regenerating means a real model load, and there is **no repo-level lever to force dark mode**: pick Dark in the app's Settings menu, or flip the OS/browser `prefers-color-scheme`. Flag it for the user rather than shipping a stale image. The committed image is the README quickstart run — its sentence on the Document tab, the default template, **Extract JSON** at temperature 0, so the Result matches README's example byte for byte — captured by headless Chrome (Playwright) at a 1512x1000 viewport, DPR 2, cropped to 60px around the content and downscaled to 1512 wide. It has **no dev toolbar**: the **Deploy** button and kebab menu advertise a hosted-deploy path this Apple-Silicon-only app does not offer, so the server ran with the one-off flag `--client.toolbarMode minimal`, which hides both. Keep them out of any re-shoot, by that flag or by cropping — never by committing `client.toolbarMode`: `minimal` removes the kebab menu, and with it the Settings entry that holds the Light/Dark/System choice (`stMainMenu` is absent from the DOM in that mode).

### `scripts/probe_mlx_vlm.py`

Standalone probe for the mlx-vlm/transformers stack. It loads the same pinned revision as the app through its own `MODEL_ID`/`MODEL_REVISION` copies — it runs as a script, so the repo root is not on `sys.path` and it cannot import `nuextract` — and `test_probe_pins_the_same_model_as_the_app` fails if either copy drifts, since a probe loading a different snapshot says nothing about the app. It calls `mlx_vlm.load()` directly, exactly as `load_model()` does after the download, so it runs on a fresh cache with no setup. Six checks:
1. `mlx_vlm.load()` succeeds on `numind/NuExtract3-mlx-8bits`
2. `processor.apply_chat_template(template=..., enable_thinking=False)` produces a rendered prompt with the typed template embedded under `【template_start】`
3. `mode='markdown'` reassigns to `【task】content` (per the model Jinja's mode-collapsing logic)
4. `mode='template-generation'` produces `【task】template generation`
5. End-to-end `mlx_vlm.generate()` returns parseable JSON for a trivial extraction
6. End-to-end `mlx_vlm.generate(image=[...])` on a PIL-rendered PNG returns typed JSON — the **only** check that runs an image through the model (mlx-vlm's numpy image processor, then the vision tower), since every test in `tests/` mocks `mlx_vlm.stream_generate`. The image is generated at run time, so no binary fixture is committed.

Run: `uv run python scripts/probe_mlx_vlm.py`. Exits non-zero on any failure.

## Key Details

- **Model**: `numind/NuExtract3-mlx-8bits` — 8-bit affine quant of NuExtract3 (Qwen3.5 4B base), ~5 GB on disk
- **Pinned model revision**: `DEFAULT_MODEL_REVISION` is a full commit SHA (`bd8048c…`, upstream `main` as of 2026-05-19) passed to `snapshot_download`, because the snapshot carries code, not just weights. mlx-vlm ≥0.6.16 executes any `model_file` a checkpoint's `config.json` declares, with no opt-in (`get_model_and_args` in `mlx_vlm/utils.py`, Blaizzy/mlx-vlm#1926); its qwen3_5 processor load defaults `trust_remote_code=True` (`install_auto_processor_patch` in `mlx_vlm/models/base.py`); and `chat_template.jinja`, which does all of the mode routing, ships in the repo. Tracking `main` would let an upstream push change what runs in-process and how every prompt renders, with every test mocked past it. It must stay a SHA — a branch or tag satisfies `snapshot_download` just as well and silently reopens the drift (`test_default_model_revision_is_a_full_commit_sha`). **To bump:** read the new `sha` from `https://huggingface.co/api/models/numind/NuExtract3-mlx-8bits`, change it in `nuextract.py` *and* `scripts/probe_mlx_vlm.py` (a test fails if they differ), and run the probe. Existing installs then fetch only the files that changed — the cache is content-addressed — which is all ~5 GB if the weights did. A pinned revision already in the cache resolves offline with no network and online with one metadata call.
- **Context**: 262K tokens declared by the model (`text_config.max_position_embeddings = 262144`), but the practical limit is bounded by unified memory + KV cache size
- **Pinned transformers**: `==5.17.0`. The floor is **not freely chosen** — `mlx-vlm==0.7.2` declares `transformers>=5.14.0`, so transformers cannot go below 5.14.0 without also downgrading mlx-vlm. (The model's own declared `transformers_version` is `5.5.4`, but `qwen3_5` only enters the auto-resolver mapping in much later versions.) The invariant that actually makes the stack work is mlx-vlm's, not transformers': importing `mlx_vlm.models.qwen3_5` must swap in mlx-vlm's own processor (see *No torch* below). `test_mlx_vlm_substitutes_its_own_processor_for_qwen3_5` gates it by running the real `mlx_vlm.utils.load` on a weightless checkpoint carrying the upstream `processor_config.json`, and fails if a bump drops the substitution, builds the processor before importing the model package, or stops reading the geometry keys. It replaced the transformers checks that used to stand here (`qwen3_5` in `CONFIG_MAPPING_NAMES`, `Qwen2VLImageProcessor` exported), which stayed green with the substitution disabled: mlx-vlm reads `config.json` with plain `json`, and `AutoTokenizer` catches the `AutoConfig` failure and falls back to a generic config, so the app's load is byte-identical without `qwen3_5` in the mapping.
- **mlx-vlm and mlx move together**: `mlx` is transitive — unpinned in `pyproject.toml`, locked at 0.32.2 — and `mlx-vlm>=0.7.0` requires `mlx>=0.32.2`. The trap is the reverse direction: mlx-vlm **below 0.6.16** passes an `mx.array` where mlx 0.32.2 now demands an int (`qwen3_vl/vision.py`'s `mx.repeat`, fixed in Blaizzy/mlx-vlm#1982), so every *image* extraction raises `TypeError` while text-only runs and the whole mocked suite stay green. Reverting just the `mlx-vlm` pin and running `uv lock` walks straight into it, because uv keeps the locked mlx 0.32.2, which still satisfies the old `mlx>=0.32.0`. Rolling mlx-vlm back therefore also needs `uv lock --upgrade-package mlx==0.32.0 --upgrade-package mlx-metal==0.32.0`, and after **any** mlx or mlx-vlm change run `scripts/probe_mlx_vlm.py` — its check 6 is the only check that runs the vision tower.
- **No torch, deliberately**: nothing in the tree depends on `torch` or `torchvision` (`uv tree --frozen --invert --package torch` prints nothing), because the app's load path never reaches transformers' Qwen processor. `mlx_vlm.load()` resolves the model package (`get_model_and_args` in `mlx_vlm/utils.py`, reached from both `load_model` and `load_image_processor`) *before* it calls `load_processor`, and importing `mlx_vlm.models.qwen3_5` wraps `transformers.AutoProcessor.from_pretrained` (`install_auto_processor_patch` in `mlx_vlm/models/base.py`) so that any checkpoint whose `config.json` says `model_type: qwen3_5` gets mlx-vlm's own numpy/PIL `Qwen3VLProcessor`, image and video processors included. Pixel values and input ids come out byte-identical with and without torch installed. It is transformers' *own* Qwen3-VL processor that needs torchvision (its `Qwen3VLVideoProcessor` raises `requires the Torchvision library`), so the old `torchvision==0.29.0` pin only ever served a path the app does not take. Do not add it back "to be safe": transformers imports torch eagerly whenever it is importable (`generation/logits_process.py`, `image_utils.py`), which cost ~1.4 s and ~280 MB RSS on `import nuextract`, plus ~580 MiB of `site-packages` across torch, torchvision, sympy, networkx, mpmath and setuptools. **One trap survives the removal**: the wrapper swallows *any* exception from mlx-vlm's processor load (`except Exception: pass`) and falls through to transformers, which then fails on this checkpoint with an error that hides the real one — `ValueError: Unrecognized image processor` on a cache holding the upstream `processor_config.json`, or an eight-line `Qwen3VLVideoProcessor requires the PyTorch library … requires the Torchvision library` on one the old shim rewrote. Neither names the cause, and installing torch is not a fix: on a rewritten cache it makes the error vanish by silently loading transformers' processor, whose pixel values differ slightly from mlx-vlm's. Surface the swallowed exception by calling `mlx_vlm.models.qwen3_vl.processing_qwen3_vl.Qwen3VLProcessor.from_pretrained(<snapshot dir>)` directly — with a corrupt `tokenizer.json`, `mlx_vlm.load` reports `Unrecognized image processor` while the direct call raises the real `JSONDecodeError`. `test_mlx_vlm_substitutes_its_own_processor_for_qwen3_5` is what notices that substitution stopping (see *Pinned transformers* above), and `test_lockfile_does_not_pull_in_torch` fails the moment `uv.lock` gains `torch` or `torchvision` again. It reads the committed lock rather than probing the environment on purpose: a `.venv` synced before the drop keeps torch until an exact `uv sync` (`uv run` syncs inexactly), and that stale local state should not fail the suite.
- **Pinned Streamlit**: `==1.64.0`. The app uses APIs newer than most training data — `st.container(horizontal=True)`, the `icon=` parameter on `st.title`/`st.subheader`, `width="stretch"` (which supersedes the older `use_container_width`), `on_click="ignore"` on `st.download_button`, and `:material/…` icon strings. **Do not "modernise" these back to older spellings** — that is a regression, not a fix, and it is the highest-probability wrong edit in this repo. Invoke the `developing-with-streamlit` skill for any Streamlit change; it loads docs matched to the installed version. **A bump also means re-verifying the dark theme's contrast assumptions** (see *Theme* below): `test_dark_theme_meets_its_contrast_floors` checks the ratios, but only against Streamlit internals it copies — the Prism token hexes in `_PRISM_TOKEN_COLORS`, the hard-coded white primary-button label, and the toggle knob drawn in `textColor` — so a release that changes those passes green while the page fails.
- **`processor_config.json` is deliberately not patched**: `numind/NuExtract3-mlx-8bits` declares `Qwen3VLImageProcessor` where the model author's own `numind/NuExtract3` declares `Qwen2VLImageProcessor` with otherwise identical geometry — a real conversion bug in the MLX repo, which a `patch_processor_config()` shim used to rewrite on every load. It was removed because nothing the app runs reads that key: mlx-vlm's `Qwen3VLProcessor` (see *No torch* above) takes only the geometry keys, and the upstream name, the rewritten one and a garbage class name all load the same classes and produce identical tensors — and the shim was already inert at mlx-vlm 0.6.13. The only reader is transformers' own `AutoProcessor`, which without torchvision fails on this checkpoint whichever name is there. The shim meanwhile had real costs: `Path.write_text` follows the snapshot symlink, so it rewrote the shared, content-addressed blob under `~/.cache/huggingface` (a blob named for one hash now holding another — true of any cache the app has already loaded), and on a read-only cache it raised `PermissionError` before `mlx_vlm.load` ever ran. **Do not reinstate it on seeing `Unrecognized image processor`**: on an unpatched cache that is what *any* failure inside mlx-vlm's own processor load looks like, because mlx-vlm swallows it and falls through to transformers — a corrupt `tokenizer.json` reproduces it.
- **Template kwarg API**: HF transformers' `apply_chat_template` accepts template variables as **direct keyword arguments** (e.g. `template="..."`, `mode="..."`, `enable_thinking=False`). The HF Space uses vLLM which expects them nested under `chat_template_kwargs={...}` — that convention does **not** apply to direct HF/mlx-vlm usage. As of transformers 5.15 this is conditional on the model's template, not universal: `apply_chat_template` introspects the Jinja for declared variables and routes anything undeclared into `processor_kwargs`, warning as it does. NuExtract3's template declares all four kwargs `render_prompt` sends, so nothing is misrouted today — but a template change (or a stricter transformers) could turn this into a silent no-op, **and the warning will not tell you**: `import mlx_vlm` sets `TRANSFORMERS_VERBOSITY=error` unconditionally (`mlx_vlm/__init__.py`), overriding the environment, so that `logger.warning` never prints in the app or the probe. To see it, call `transformers.logging.set_verbosity_warning()` after importing mlx_vlm — or rely on assertions against the rendered prompt, as probe checks 2-4 do.
- **Unexercised transitive paths**: the dependency set carries `pandas` 3.x and `pyarrow` 25.x (Streamlit's dataframe/Altair/Arrow rendering), `opencv-python` 5.x (mlx-vlm's video path), and `mlx-audio` 0.5.x (mlx-vlm's audio path — a 0.x minor, so breaking by semver). Nothing in this app or its tests touches any of them, so each crossed a breaking version **unverified rather than verified** — a regression there would surface to a user, not to CI.
- **Modes** (from the model's `chat_template.jinja`, which ships inside the HF snapshot — **not in this repo**, so grepping for it locally finds nothing): setting `template=...` forces `mode='structured'`; `mode='markdown'` is reassigned to `'content'`; `mode='template-generation'` and `'document-detection'` are also valid. `enable_thinking=True` is only allowed for `structured` and `content` modes.
- **Output parsing**: NuExtract3 may emit `<answer>...</answer>` wrappers around structured output or raw JSON. `extract_answer_block` handles both.
- **Reasoning trace**: model emits `<think>...</think>` before the answer when `enable_thinking=True`. `split_reasoning_and_output` separates them for the two-pane UI.
- **Image input**: `st.file_uploader` (jpg/jpeg/png/webp), persisted to a temp file before passing to mlx-vlm. No clipboard support (Streamlit limitation vs the Gradio-based HF Space).
- **Theme**: `.streamlit/config.toml` customises **dark mode only** ("Graphite & Cobalt": `[theme.dark]` + `[theme.dark.sidebar]`, colours only), so Light is byte-identical to stock and the Settings menu still offers Light/Dark/System. **The initial theme is the visitor's, not ours** — Streamlit resolves System from `prefers-color-scheme` — which is why a single dark screenshot can misrepresent the app. Three rules, all gated by `test_theme_config_customises_dark_mode_only`: **no root `[theme]` keys**, because Streamlit builds each mode as root `[theme]` merged with that mode's section (`yn` in the 1.64 bundle's `utils.*.js`), so a root key restyles Light too; **no `[theme.light]`**, which would stop Light matching stock; and **no dark-only fonts, radii or borders**, so the two modes share one shape. Contrary to what this file used to say, a variant section does *not* need its twin — either `[theme.light]` or `[theme.dark]` alone makes Streamlit build all three choices (`xn`, verified in a browser); it is root keys *without* any variant section that lock the app to one mode. The palette is pinned by hard constraints its comments document and `test_dark_theme_meets_its_contrast_floors` enforces: the primary button label is hard-coded white (so `primaryColor` sits in a narrow luminance band — white ≥ 4.5:1, yet ≥ 3:1 on the canvas and on inputs), `st.code`'s syntax colours are fixed Prism hexes rather than theme keys (so `codeBackgroundColor` must stay dark enough for the `null` token `#1c83e1`, which stock dark fails at 4.36:1), and the sidebar toggle knob is drawn in `textColor`, not white. The palette came out of a judged comparison of five candidates in a model-free replica of this layout; lifting the canvas, recessing the code wells and moving the accent off red (which collided with `st.error`) were the deliberate changes. It replaced stock themes, which themselves replaced a GitHub-inspired palette that carried shape keys too and failed the same two contrast checks as stock dark. `.gitignore` ignores `.streamlit/secrets.toml` only, so config.toml is tracked.
- **No PDF support** in v1 — matches the HF Space; users convert PDFs to images externally.

The NuExtract3 model weights are separately **Apache-2.0** and downloaded at runtime (not redistributed by this repo), so the model license governs model usage, not this project's code. - **`tests/conftest.py`** — path setup, plus a session-scoped autouse fixture that replaces `nuextract.snapshot_download`, `nuextract.mlx_vlm_load` and `huggingface_hub.snapshot_download` with stand-ins that raise. A test that forgets to mock now fails in milliseconds with a message naming the fix, instead of pulling 4.8 GB. Tests that legitimately exercise those boundaries patch over the guard and restore it on exit, so it is safe always-on. Deliberately **narrow**: banning sockets outright would also catch this, but Streamlit gathers usage stats and AppTest runs the real script in-process, so a broad network ban risks failures unrelated to the bug being prevented. `test_nuextract.py::test_conftest_guard_blocks_a_forgotten_mock` is the regression test for the guard itself.

- **`tests/test_nuextract.py`** (44) — Pure function tests for the runtime wrapper. `extract_answer_block` and `pretty_json_or_text` cases are parametrized; integration boundaries (`load_model`, `stream_extract`) are tested by patching the `nuextract.*` namespace. Three tests hold the model pin: the default call passes `DEFAULT_MODEL_REVISION`, that value is a 40-hex SHA, and the probe's copies match (read with `ast`, so the probe is never imported). One test builds a real mlx-vlm processor through `mlx_vlm.utils.load`, with only weight loading stubbed, from a weightless `tmp_path` checkpoint, to gate the qwen3_5 processor substitution (see *Pinned transformers* in Key Details) — the only test that runs a real dependency rather than a mock. It loads no weights, needs no HF cache and makes no network call. Next to it, `test_lockfile_does_not_pull_in_torch` asserts the committed `uv.lock` names neither `torch` nor `torchvision`.
- **`tests/test_streamlit_app.py`** (32) — Helper function tests, plus two that read `.streamlit/config.toml` directly (the dark-only structure and the contrast floors — see *Theme* in Key Details; neither uses the `app` fixture). The module-scoped `app` fixture mocks all Streamlit primitives so `streamlit_app` imports cleanly without a real model (`st.fragment` is patched to an identity decorator so the `_output_section` fragment body runs under the mocks). It enters them through a `contextlib.ExitStack` rather than one `with` statement: the 8 `_ST_NOOPS` are entered in a loop, and the 21 context managers sit **exactly at** CPython's statically-nested-block ceiling (measured on both 3.12 and 3.13: 21 compiles, a 22nd fails at *collection* with `SyntaxError: too many statically nested blocks`). Adding one more patch is what breaks a flat `with`, so keep the ExitStack. **It patches `nuextract.load_model` / `snapshot_download` / `mlx_vlm_load`, never `streamlit_app.load_model`**: `patch("streamlit_app.X")` resolves its target *by importing* `streamlit_app`, whose module body calls `get_model()`, so the real 4.8 GB download fires during patch setup — before the mock exists — and the fixture's subsequent `sys.modules.pop` + re-import rebinds `load_model` from `nuextract` and discards the mock anyway. Patch the dependency, not the consumer; the `conftest.py` guard now makes the mistake fail loudly rather than silently. `st.empty` is stubbed with `side_effect`, not `return_value`, because `_output_section` calls it once per pane (output and download, plus reasoning while the toggle is on — off in this fixture, whose `session_state` is empty) and one shared mock would let output routed to the wrong pane still assert clean. Includes a regression test that removing an upload cleans up the orphaned temp file and session state.
- **`tests/test_streamlit_app_apptest.py`** (36) — End-to-end UI wiring via Streamlit's `AppTest`. The three model-loading stubs live in one `_stub_model_loading(monkeypatch, *, on_load=None)` helper shared by the `at` fixture and the ordering guard, so the set of stubbed boundaries is defined once — a second copy drifts, and a missed boundary fails as a 4.8 GB download rather than an obvious error. The `at_with_image` fixture drives a fake image into `st.file_uploader` via AppTest's native `set_value` API (added in Streamlit 1.56), exercising the real widget. Covers initial render (including the Result-pane empty-state hint rendered by the `_output_section` fragment, the model-load ordering guard described under Top-level UI, and the layout contract — which sidebar region or tab holds each keyed widget, and a Reasoning pane that exists only while its toggle is on), button validation, and streaming flow for text- and image-input paths (including the instructions field, template-gen system prompt, and template-gen reasoning override). `at.download_button` **is** exposed by AppTest (`streamlit/testing/v1/app_test.py`) and does surface the button rendered into the `st.empty()` placeholder — the file's decision not to assert it is a coverage gap, not a framework limit. AppTest's `DownloadButton` carries only `label`/`help`/`value`, so `file_name`/`mime`/payload assertions stay in `test_streamlit_app.py`.
